### Rules that constrain every task

- All game quantities and mechanics need two independent agreeing sources, source version/date and provenance. Two renderings of one upstream are not automatically independent. Recheck independence even where historical comments describe it loosely. Structural checks can reject impossible values but cannot establish provenance.
- Withhold conflicts, missing values and unreleased/beta entries. A roster label, parsed prose or numerical plausibility is insufficient. Research completion can correctly mean “still withheld.”
- No character-name/character-ID/ability-ID behavior branches in the engine. IDs are references, never special-case dispatch keys. New reusable capability first, then sourced character data.
- Keep game definitions and conditions as serializable plain data; engine/mechanics rule evaluators may be functions inside their own layers. Existing function-valued `SimulationConfig` resolver seams require a Worker boundary adapter; they cannot be posted directly as JSON.
- Deterministic authored artifact stats only. Artifact substat roll RNG is excluded. No hidden simulator RNG or random optimization starts.
- Optimizer uses engine legality and simulation results. It never duplicates damage, reactions, energy, cooldown or survival math. Frontend only displays and configures these contracts.
- Public seam changes are additive where possible: enumerate callers, manager reviews, owner implements, architecture and migration tests follow. Character/shared types need an explicitly assigned owner because the historic ownership table does not allocate every new path.

## 2. Architecture decisions to make before expansion

### 2.1 One simulation clock and an ordered event queue

Retain seconds at the public boundary initially. ENG-001 evaluates an integer tick representation or a canonical time representation against existing values before changing internal units; do not assume every measured timing is an exact frame or silently round imported timings. The scheduler needs a total ordering such as `(time, documented phase, insertion sequence)` with stable source/target iteration. The phase order is an engine convention until game evidence establishes a rule for a particular interaction. Do not present a deterministic simultaneous reaction convention as universal game priority.

Actions schedule effects; advancing to the next decision time processes every due event. A delayed hit can land after a swap, during another cast, or after the final authored action. Event processing must read the state valid at the event time. Buff expiry, arrivals, summons, fields, reaction ticks and enemy events use this same clock. Queue entries carry causal parent IDs and cancellation/generation tokens so refresh/replacement cannot leave stale events alive.

Define three separate times: action sequence end, simulation horizon, and last processed event. The default product score must identify its denominator. A fixed-window damage/DPS comparison uses the same horizon for every rotation; an early-ending prefix must not gain an unexplained DPS advantage. Events beyond the horizon remain pending in a checkpoint and do not contribute to in-window damage. The precise inclusion rule at the horizon is a versioned contract with boundary tests.

### 2.2 State, checkpoint and result are different objects

A checkpoint contains every fact affecting future execution: canonical clock, active actor, action lock, cooldown/charge state, energy, HP, stamina, resources and per-stack expiry, ICD, auras and drains, buffs, captured stats, stance/infusion state, proc counters, summons/cores/fields, pending particles/events, enemy phase/HP/shields, target relations, and queue sequence state. The exact set grows only with implemented capabilities. Do not serialize imaginary unused fields as proof of support.

Result data includes aggregates and an optional detailed trace; it is not the source of runtime truth. Checkpoint identity includes engine/schema/data version and the scenario/build fingerprint. A changed equipment configuration invalidates a prefix checkpoint. Old permissive snapshots that ignore unknown character IDs may remain as explicitly legacy behavior; optimizer checkpoints require a matching configuration.

Current same-input full runs are deterministic. Current cold-vs-resumed runs are **not** byte-identical because aura decay re-anchors floating-point calculations; existing tolerance applies. ENG-002 will preserve canonical decay anchors where practical and prove stronger equality before promising it. Numeric tolerance cannot excuse a different reaction, legal-action decision, owner, event count or branch. Boundary-equivalence tests must assert those discrete outcomes exactly.

### 2.3 A small typed capability language, not a scripting language

Extend `GenericCharacterDefinition`, `KitAbility`, `Buff`, `StateEffect` and existing trigger/stance/infusion types. Avoid replacing them with a general interpreter in one migration. A normalized compiled plan may resolve references and validate capabilities once per configuration, but cannot smuggle executable character callbacks across the data seam.

Proposed capability families:

| Family | Declarative information | Rules owned by |
|---|---|---|
| Action | availability, slot/variant, cast/lock/cancel windows, resource costs, cooldown/charges, normal-string transitions | Combat execution; sourced timing data |
| Effect | trigger event, source/target scope, existing conjunctive conditions, bounded effects, per-event/interval proc cap | Mechanics semantics + engine dispatch |
| Resource/stack | owner, initial/cap, gain/spend/set, refresh policy, per-stack vs shared expiry, transfer/reset rules | Shared contract, combat runtime |
| Damage/heal/shield | scaling terms, talent tables, eligible modifiers, source credit, target selection | Mechanics formula + combat execution |
| Aura/reaction | application gauge, ICD domain, reaction ownership, persistent reaction state | Mechanics |
| Actor/entity | summon/core/pickup/field, lifetime, replacement group/cap, scheduled behavior, targeting | Combat lifecycle + mechanics effects |
| Mode | stance, alternate abilities, infusion priority, on/off-field continuation, exit conditions | Existing stance/infusion abstractions extended |
| Condition | Existing conjunctions over typed comparisons; extend comparison inputs to resources, HP, active actor, target state, event tags and elapsed time as needed | Mechanics, pure data evaluator |
| Capture | which stat/effect channels capture, when capture/refresh occurs, which target modifiers stay dynamic | Mechanics policy + combat storage |

Schema validation rejects unknown references, unsupported capabilities, cyclic unbounded triggers, non-finite values, invalid source/target scopes and impossible ranges. Runtime event budgets catch malformed definitions with a structured failure; they are safeguards, not in-game mechanics. Synthetic test kits prove reusable capabilities. Real kit acceptance separately needs sourced values and full integration tests.

The prior manager decision deliberately leaves OR inexpressible and uses multiple buffs for alternatives, avoiding a predicate language. Preserve existing conjunctions and multiple-buff authoring first. Any proposed all/any/not condition tree requires an explicit design reconsideration supported by concrete sourced kits that cannot be expressed correctly with those existing patterns; it is not an accepted extension in this plan.

### 2.4 Expected crit and conditional randomness

Current `critMode: expected` is useful when crit changes only a linear damage term and cannot alter subsequent state. If a crit grants particles/stacks, resets a cooldown, crosses HP thresholds or changes a time-to-kill decision, substituting average damage or average resource gain can produce a state no actual run reaches. In general, executing on an expected state does not equal the expected outcome of executing branches.

MECH-012 must classify effects into: deterministic effects; linear expected-only damage; outcome-dependent effects that remain unsupported in default mode. Optional future exact finite branch enumeration could remain deterministic but needs explicit state merging, branch-mass accounting, cost bounds and semantics for reporting distributions. It is research, not a hidden permission to add sampled RNG. Forced crit/noncrit runs are explicit scenarios and are not a substitute for a claimed exact expectation. Equipment with conditional random procs follows the same rule. Do not imply a particular expected-damage kill time is an expected actual kill time.

### Existing code observations requiring early regression work

These are scoped planning findings, not patches applied here:

1. `simulateRotation.ts` loops over every delayed hit of the current action before advancing to the next action, then sorts the timeline. ENG-001/003 should include a fixture where the next action changes the aura before the previous action's delayed hit lands; a sorted trace alone cannot prove state correctness.
2. `snapshot()` includes `activeTriggers` and `activeInfusions`, but the inspected initialization creates empty arrays and `restoreFromSnapshot()` returns clock/auras/unknown characters without those arrays. ENG-002 must reproduce their continuation explicitly and audit state key coverage, rather than assuming stance restoration recreates all effects.
3. `ResourceDefinition` says expiry returns to `initial`, while `resourceValueAt()` returns zero. Clarify intended schema semantics with a nonzero-initial synthetic resource; do not change behavior without owner/contract review.
4. Buff snapshot comments still describe a one-hit engine despite existing multi-hit data. MECH-005 must inventory actual behavior, separate stale documentation from executable support and add cast-before-buff-expiry/late-hit tests.

### Formal character completion contract

“All playable characters” is a coverage program, not a parser count. A released identity/form is complete for a declared scenario only when:

1. Identity/form handling, level/ascension/base curves, talent tables, equipment compatibility and constellation gates are validated. Traveler remains one identity with forms; team uniqueness uses identity, not display name or form ID.
2. Every relevant cast variant, hit timing, application/ICD, resource and lifecycle rule is either executable with evidence or explicitly listed as unsupported. High multiplier accuracy cannot compensate for missing summon uptime or hit count.
3. The kit executes through reusable types. Capability-specific contract tests cover at least synthetic boundary cases and sourced character integration; no single-character workaround enters the engine.
4. A support manifest distinguishes numeric provenance, mechanic coverage and website connection. Counts are derived from the actual current registry; this document does not freeze historical roster/perk totals as future truth.
5. Build level, constellation, weapon and artifact changes survive normalization and measurably affect the correct execution channels. Inactive/locked effects remain inactive. Stat buffs preserve base-stat precedence.
6. Benchmark rotations include solo isolation, team buff/reaction interaction, normal/alternate mode, off-field continuation and checkpoint replay. Comparisons to outside calculators distinguish differing assumptions instead of fitting constants to match totals.

### Search correctness and performance notes

- **Fixed work versus wall clock:** simulator time is virtual and deterministic. Search may have a wall-clock cancellation request for responsiveness, but a wall-clock cutoff can explore different nodes on different machines. Such partial output must record completed deterministic work and may not claim same-result reproducibility from elapsed seconds alone. Stable work budgets and stable result merging are the reproducible mode.
- **State equivalence:** a key must preserve future behavior and any path summary needed by the objective/constraints. Same future combat state with different damage-so-far can retain the better prefix for a single additive objective; Pareto objectives, field-time constraints, required actions and diversity may require additional labels. More than combat state can matter.
- **Pending damage:** prefixes with summons or future reaction ticks cannot be fairly scored by eagerly flushing each node to the horizon and then resuming at an earlier decision time. Keep search checkpoints at the actual decision time; use a separate terminal evaluation copy or a clearly identified heuristic estimate. No double-counted pending damage.
- **Build legality:** equipment can change energy availability and, as new capabilities arrive, cooldowns, charges, stamina, HP/resource thresholds, triggers and ability availability. The older shorthand that builds change only scoring, or legality only through ER, must not constrain the future design. Full replay is required for every build; prefix snapshots are configuration-specific.
- **Dominance pruning:** a piece with more of every ordinary stat is not universally superior when HP thresholds, caps, conversion rules, effects, inventory availability or conditional behavior differ. Apply dominance only inside a proved monotone equivalence class; otherwise keep both. Stat-bag equality is insufficient when passives differ.
- **Optimization limits:** beam search is incomplete; a wider beam can change pruning paths and need not improve results unless a compatible incumbent is retained. Alternating heuristic passes do not prove a local optimum unless each pass actually solves its coordinate subproblem. Team/build search compounds these limitations and must report budgets and starting candidates.

## 7. Validation and evidence strategy

### Layer and integration coverage

- Mechanics: independently worked source fixtures, thresholds, clamping, ordered modifier composition, conservation rules where applicable and source-version assertions.
- Engine: action legality and same-time order; traces with delayed hits crossing swaps; event tail/horizon; entities/particles between actions; finite work; snapshots split at every decision boundary; no mutation of input/team/scenario/checkpoints.
- Search: cold-replayed emitted result, constraints, complete keys, deterministic enumeration/merges, bounded work, small exhaustive oracle, repeatable loop feasibility, build-specific legality and missing-capability handling.
- End-to-end: four configured characters → normalized builds/effects → simulation/search → totals/timeline → exported request → replay. Mutate bindings in an isolated copy where useful; a test proving a pure formula works does not prove the website supplies the selected values.
- Data: two-source replay and structural validation; unsupported effect counts tied to actual execution support. Test source conflict withholding and an effect that is validly parsed but not executable.

### Representative fixture matrix

Use small synthetic kits to isolate contracts and sourced real kits to validate integration. Include direct carry, off-field damage with driver, infusion/stance replacement, independent stack expiry, HP drain/heal, shield reaction, energy-constrained team, delayed projectile/particle, persistent reaction/core, multiple target aura patterns, immunity window and repeated encounter wave. Do not invent kit values to fill the matrix; a synthetic quantity is explicitly labelled a test parameter.

Every benchmark records engine/data version, scenario, work counts, events, memory/serialization size and observed runtime. Count-based regression limits are primary CI guards. Machine-dependent timing is measured on a named environment and used as a performance signal, not proof of determinism. Large full-trace rendering and data-bundle cost are separate frontend budgets.

### Acceptance gate for a mechanic or search capability

A capability cannot be marked supported merely because its type exists, constants are present, a unit test passes or a presentation table says `modelled`. Acceptance requires: source eligibility; schema validation; actual execution; snapshot and resume; search-key/legality participation if relevant; trace/aggregate attribution; product adapter connection if exposed; documented limitations; focused tests plus the repository's required integration gates. The owner reports the canonical eight fields, and the manager records what was actually accepted.

## 8. Risks and decisions kept explicit

1. **Current documentation overstates completeness in places.** Preserve historical records, but future dispatch relies on current code and dated acceptance. This plan records specific runtime gaps instead of inheriting “engine complete” or “all reactions complete.”
2. **A global scheduler is a semantic migration.** Isolate it from HP/multi-target changes; begin with existing behavior, delayed-hit correctness and EC. Avoid a one-shot engine rewrite.
3. **Arbitrary-time snapshots are larger than decision-boundary snapshots.** First guarantee optimizer decision-boundary resume; enable pausing inside casts only after action lock/cancel state and pending events are serializable.
4. **Unknown source values can block a character but need not block a reusable capability.** Synthetic contracts proceed; public game support waits. A closed research task may leave the mechanic unsupported with a better explanation.
5. **Geometry and reaction order are fidelity choices.** Start with explicit deterministic target relationships and scripted scenarios. Do not promise full enemy AI, physics or universal simultaneous reaction priority without evidence.
6. **Search output quality depends on model coverage.** Unsupported meaningful effects can change ranking. Report affected candidates/scenarios; a precise numeric score is not evidence of complete gameplay fidelity.
7. **Future build/team search scope is a planned extension.** Its sequence is concrete here, but implementation should follow the product plan's priority and data readiness. Existing artifact RNG exclusion remains unchanged.
8. **No calendar estimate is supplied.** Estimate after ENG-001/002 audits and measured search/data workload; task sizes depend heavily on evidence availability and semantic migration findings.
